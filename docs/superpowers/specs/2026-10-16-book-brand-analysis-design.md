# 도서 브랜드 분석 기능 확장 설계

작성일: 2026-10-16
대상 저장소: 이 저장소(`isnow890/naver-search-mcp` 포크). 원본은 `upstream` 리모트, 작업 브랜치는 `feature/book-brand-analysis`.

표기: **[결정]** 사용자가 정한 것, **[내 판단]** 설계자(Claude)가 정한 것(검토 필요), **[빌더 몫]** 구현자가 정할 것.

## 1. 의도와 이유

도서 제품 브랜드(예: "그래머인사이드" vs "천일문 중등 그래머")를 대상으로 다음을 분석한다. **[결정]**

1. 어느 시기에 검색량과 쇼핑 클릭이 늘어나는가 (검색어 트렌드, 쇼핑 인사이트)
2. 그 시기에 블로그, 카페에서 어떤 언급이 늘었는가 (근거 수집)
3. 어떤 브랜드와 같이 언급되는가

분석 대상은 출판사가 아니라 **제품/시리즈 단위**의 이름이다. 같은 카테고리(중등 영어 문법 교재)에서 경쟁하는 상품끼리 비교한다.

사용 방식은 Claude가 MCP 도구를 호출해 분석하고, 결과를 대화로 보여주며 요청 시 파일로 저장하는 것이다. **[결정]**

## 2. 목표 / 비목표 / 안티 목표

**목표**
- 브랜드 여러 개를 한 척도로 비교한 시계열 지수 제공
- 블로그/카페 언급 글의 월별 분포와 동시 언급 브랜드 후보 제공
- 결과를 엑셀(.xlsx)과 CSV로 저장 **[결정]**
- 비교할 브랜드를 사용자가 직접 지정하거나, 후보를 자동으로 뽑아 고르는 두 방식 지원 **[결정]**

**비목표**
- 한국어 NLP를 서버에 내장해 브랜드명을 자동 판별하는 것 **[내 판단]** (후보 추출까지만 서버가 하고, 판별은 호출한 Claude가 한다)
- 실제 검색 횟수(절대량) 제공. API가 상대값만 주므로 불가능하다
- 뉴스, 이미지, 지식iN, 백과, 지역 검색 기능 개선 (기존 그대로 두고, 노출만 끌 수 있게 한다)

**안티 목표 (기술적으로 동작해도 실패로 보는 것)**
- 상대 지수나 근사치를 실제 검색량이나 정확한 언급 건수처럼 보이게 하는 것. 결과에는 항상 "상대 지수", "수집 표본 기준 근사" 같은 한계 표시가 붙어야 한다 **[내 판단]**
- Data Lab 월 호출 한도(검색어 트렌드, 쇼핑 인사이트 각각 월 5만 건)를 모르는 사이에 소진하는 것
- API 키가 로그, 에러 메시지, 파일 결과물에 노출되는 것

## 3. 제약

- 인증: NAVER API HUB 키(`NCP_APIGW_API_KEY_ID`, `NCP_APIGW_API_KEY`). 기존 코드의 인증 처리(`src/config/credentials.ts`)를 그대로 쓴다. **[결정]**(env 방식), 원본 코드 재사용은 **[내 판단]**
- 언어/런타임: TypeScript, Node 18 이상, 기존 MCP SDK. 원본 저장소가 이미 그렇다.
- 호출 한도: 검색 월 775,000건, API Key당 50 RPS. Data Lab은 검색어 트렌드와 쇼핑 인사이트 각각 월 50,000건.
- API 사양(NAVER API HUB 문서 기준)
  - 검색어 트렌드: `keywordGroups` 최대 5개, 그룹당 키워드 최대 20개. `ages`는 코드 `1`~`11`.
  - 쇼핑 인사이트: 분야 `category` 최대 3쌍. 분야별 `ages`는 `10`~`60`(10단위). 키워드 API는 분야 코드가 필요하다.
  - 블로그/카페/웹 검색: `display` 1~100, `start` 1~1000(즉 키워드당 최대 1,000건), `sort`는 `sim`/`date`, 기간 필터 없음.
- 호출 한도와 별개로, 상대 지수(`ratio`)는 요청 하나 안에서 최댓값이 100이 되는 값이다.

## 4. 결정 사항 (사용자가 정한 대로)

- **기준 키워드 보정**: 매 요청마다 기준 키워드 1개를 고정하고 나머지 자리(최대 4개)를 바꿔 가며 호출해 한 척도로 환산한다. 결과는 공통 기준 대비 상대 지수다.
- **브랜드 목록**: 직접 지정하는 경우와 언급 글에서 후보를 뽑아 쓰는 경우 모두 지원한다.
- **출력**: 대화 응답 + 엑셀(.xlsx) + CSV.
- **포크 방식**: 원본 수정은 최소화하고 새 기능은 새 파일로 추가해, 원본 업데이트를 병합하기 쉽게 한다.

## 5. 설계 (대부분 내 판단 — 검토 필요)

### 5.1 브랜드 입력 형식
브랜드 하나는 `{ name, aliases[] }`다. 표기가 갈리기 때문이다(예: "그래머인사이드", "그래머 인사이드", "Grammar Inside"). 검색어 트렌드 API의 `groupName`과 `keywords[]`에 그대로 매핑된다.

### 5.2 추가할 도구 (분석 도구 2개 + 내보내기)

1. **브랜드 비교 트렌드** (검색어 트렌드와 쇼핑 인사이트를 모두 지원)
   - 입력: 브랜드 목록, 기간, 단위(일/주/월), 기기/성별/연령(선택), 쇼핑의 경우 분야 코드
   - 동작: 기준 브랜드를 정하고, 브랜드를 4개씩 나눠 호출한 뒤 기준 브랜드의 값으로 환산한다.
   - 기준 브랜드는 기본적으로 비교 대상 중 **중간 규모**인 것을 자동 선택한다(사전 호출로 규모를 가늠). 사용자가 직접 지정할 수도 있다.
   - 비교 대상보다 규모가 너무 작아 지수가 0에 가깝게 나오는 브랜드는 경고를 붙인다.
   - 출력: 기간별, 브랜드별 환산 지수, 사용한 기준 브랜드, 경고, 사용한 호출 수.

2. **언급 분석**
   - 입력: 브랜드 목록(또는 검색어), 대상(블로그/카페/웹문서), 수집 건수 상한
   - 동작: 날짜순(`sort=date`)으로 최대 1,000건 수집 → 제목/요약에 별칭이 **실제로 들어 있는 글만** 남겨 노이즈 제거(일반 단어 "그래머" 등) → `postdate` 기준 월별 건수 집계 → 같이 나온 후보 단어(공출현)와 그 단어가 나온 문장 몇 개를 반환.
   - 브랜드 최종 판별은 호출한 Claude가 한다. 확정된 브랜드는 다시 "브랜드 비교 트렌드"나 "언급 분석"의 입력으로 쓴다.
   - 출력: 월별 언급 건수(근사, 수집 표본 기준 표시), 동시 언급 후보 목록(빈도, 예시 문장), 필터로 제외된 글 수.

3. **내보내기**
   - 위 두 도구의 결과를 .xlsx와 .csv로 저장한다. 도구 인자로 저장 여부와 파일명을 받거나, 결과를 받아 저장하는 별도 도구로 만든다 **[빌더 몫]**.
   - 저장 위치는 환경변수 `NAVER_EXPORT_DIR`(기본값은 현재 작업 디렉터리 아래 `exports/`)로 한다.
   - 엑셀 라이브러리는 `exceljs`를 쓴다. 기존 `package.json`의 `xlsx@0.18.5`는 알려진 보안 취약점이 있는 것으로 알고 있어(구현 시 재확인) 쓰지 않으며, 사용되지 않으므로 제거를 검토한다.
   - 엑셀에는 "상대 지수/근사" 한계 문구를 시트에 포함한다.

### 5.3 캐시와 호출 한도 보호
- 동일 요청(엔드포인트, 파라미터)의 응답을 로컬 파일로 캐시한다. TTL은 기본 24시간, 환경변수로 조정 가능하게 한다.
- 도구는 호출 전에 필요한 호출 수를 계산해 두고, 결과에 "이번 작업에서 사용한 호출 수"를 포함한다.
- 월 한도에 접근했는지 서버가 자체 집계해 경고할지는 **[빌더 몫]**(NAVER API HUB 콘솔의 Usage Statistics를 대체할 수는 없다).

### 5.4 도구 노출 제어
- 환경변수로 노출할 도구를 제한할 수 있게 한다(예: 허용 목록). 기본값은 기존 도구 전체 + 새 도구다. 사용자가 뉴스/이미지/지식iN/지역 검색을 끌 수 있다.

### 5.5 원본과의 경계 (병합 용이성)
- 새 코드는 `src/analysis/`, `src/export/`, `src/cache/` 아래 새 파일로 추가한다.
- 기존 파일 변경은 `src/index.ts`의 도구 등록 부분과 `package.json`(의존성) 정도로 한정한다.
- 기존 `NaverSearchClient`가 제공하는 메서드를 호출만 하고 수정하지 않는다.

## 6. 빌더 몫으로 남기는 것

- 기준 브랜드 자동 선택과 환산의 정확한 알고리즘, 지수가 0에 가까운 브랜드 판정 기준
- 쇼핑 인사이트의 키워드별 API(분야 + 키워드)에서 브랜드 그룹 수 제한과 호출 분할 방식
- 동시 언급 후보 추출 방식(토큰화 방법, 불용어 처리, 후보 개수), 한국어 형태소 분석기를 쓰지 않는 선에서
- 캐시 저장 형식과 위치, 도구 노출 제어 환경변수의 이름과 형식
- 내보내기를 별도 도구로 할지 인자로 할지
- 테스트 구성(기존 `tests/` 방식을 따를 것)

## 7. 검증이 필요한 사실

구현 단계에서 실제 키로 확인해야 한다. 문서만으로는 확인되지 않았다.

- 원본 코드가 쓰는 HUB 쇼핑 인사이트 하위 경로(`/shopping/v1/category/device` 등)가 실제로 유효한지. 저장소의 `scripts/smoke-endpoints.mjs`로 확인할 수 있다.
- 웹문서(`webkr`)와 카페글(`cafearticle`)의 HUB 경로(`/search/v1/webkr`, `/search/v1/cafearticle`)가 유효한지.
- `postdate` 형식(블로그), 카페글 응답에 날짜 필드가 있는지. 카페글에 날짜가 없다면 카페는 월별 집계가 불가능하므로 설계를 조정해야 한다.
- 쇼핑 분야 "도서 > 학습/참고서"에 해당하는 분류 코드(`find_category`와 `data/categories.json`로 확인).

## 8. 알려진 한계 (결과물에 명시할 것)

- 모든 지수는 **상대값**이며 실제 검색/클릭 횟수가 아니다.
- 월별 언급 건수는 키워드당 최대 1,000건 수집 표본에서 계산한 **근사치**다.
- 동시 언급 브랜드는 단어 공출현으로 만든 **후보**이며, 정확한 브랜드 목록이 아니다.

## 9. 검토 후 확정한 설계 판단 (모두 내 판단 — 검토 필요)

검토자(구현자 관점)의 질문에 대한 답이다. 사용자 결정이 필요한 항목은 없었다.

1. **호출 예산과 확인 절차**
   - 일반적인 비교 대상은 브랜드 2~10개로 가정한다. 브랜드 수를 n이라 하면 기준 브랜드를 제외한 n-1개를 4개씩 나눠 호출하므로, 검색어 트렌드 호출은 대략 `ceil((n-1)/4)`회다. 기준 선택용 사전 호출이 추가된다.
   - 도구는 실행 전에 예상 호출 수를 계산한다. 한 번의 실행이 기본 상한(30회, 환경변수로 조정)을 넘으면 실행하지 않고 예상 호출 수를 알려 준다. 사용자가 명시적으로 승인하는 인자를 주어야 진행한다. `dryRun` 인자로 호출 없이 예상 수만 볼 수 있다.
   - 캐시에 있는 응답은 호출 수에 포함하지 않는다.
2. **기준 브랜드와 지수 0 문제**
   - 기준 브랜드는 모든 호출에 고정 슬롯으로 넣고, 나머지 최대 4개 슬롯만 교체한다(§4 결정 그대로).
   - 비교 대상의 규모 차이가 커서 어떤 브랜드의 환산 지수가 기준 대비 임계값(기본 1 미만) 이하이면, 도구가 기준 브랜드를 더 작은 브랜드로 바꿔 **한 번 자동 재시도**한다. 그래도 해결되지 않으면 해당 브랜드에 "정밀도 낮음" 경고를 붙여 반환한다. 이 임계값은 구현자가 데이터를 보고 조정해도 된다.
3. **카페글에 날짜 필드가 없는 경우**
   - 카페글 응답에는 작성일이 없을 가능성이 높다(확인 필요, §7). 없다면 카페는 **월별 집계에서 제외**하고, 카페 전체 건수(`total`)와 동시 언급 후보 분석만 제공한다. 월별 분포는 블로그 기준으로만 낸다. 결과에 이 사실을 명시한다.
4. **HUB 경로 검증은 첫 단계의 관문**
   - 구현 계획의 첫 작업은 §7의 사실을 실제 키로 확인하는 것이다. 키는 사용자가 NAVER API HUB 키를 환경변수(`NCP_APIGW_API_KEY_ID`, `NCP_APIGW_API_KEY`)로 제공해야 한다. 이 검증 결과에 따라 나머지 계획을 조정한다.
5. **쇼핑 인사이트 결과가 비어 있는 경우**
   - 브랜드명 키워드가 해당 분야에서 데이터를 거의 주지 않을 수 있다. 결과가 비었거나 지수가 지나치게 낮으면 오류로 처리하지 않고 "해당 분야에서 데이터 없음/희소" 경고와 함께 빈 결과를 반환한다. 분야 단위 데이터로 자동 대체하지는 않는다. 필요하면 사용자가 분야 단위 도구를 따로 호출한다.
6. **언급 분석의 후보 출력 형식**
   - 후보 단어마다 전체 빈도, 브랜드별 공출현 빈도, 예시 문장(최대 3개), 출처 유형(블로그/카페)을 반환한다. 후보 개수는 기본 상위 30개다.

| `/search/v1/webkr`, `/search/v1/cafearticle` | 유효. 응답 구조는 블로그와 같다 (`lastBuildDate,total,start,display,items`) |
| 블로그 `postdate` | `YYYYMMDD` 문자열 (예: `20261017`) — 구현의 가정이 맞았다 |
| 카페글 / 웹문서 날짜 필드 | **없음** (카페: `title,link,description,cafename,cafeurl` / 웹: `title,link,description`). §9-3의 대체 동작(월별 집계는 블로그만)이 그대로 적용된다 |
| 쇼핑 키워드 그룹 최대 개수 | **5개** (6개는 HTTP 400 `.keyword -> should NOT have more than 5 items`) — `SHOPPING_SLOTS_PER_CALL = 5` 확정 |
| 쇼핑 분야 코드 | `50005951` (도서 > 국어/외국어 > 영어 > 문법/독해/작문). `data/categories.json`에서 확인. 중등 교재는 `중학교 참고서 > 중1~3 문제집/자습서` 코드도 있다 |
| 쇼핑 키워드 응답 | `results[].keyword` 에 키워드가 에코되고 `data`는 `[{period, ratio}]`. 이 분야에서 "그래머인사이드" 단독 호출은 `data`가 **빈 배열**이었다 (희소 데이터) → §9-5의 "데이터 없음/희소" 경고 경로가 실제로 쓰인다 |

추가 확인 (Task 10, 종단 실행): 쇼핑 인사이트 키워드 그룹의 param은 **1개만** 허용된다 (2개 이상은 HTTP 400 .keyword[0].param -> should NOT have more than 1 items). 별칭을 쓸 수 없으므로 쇼핑 비교는 브랜드 이름 하나만 사용하고 (SHOPPING_KEYWORDS_PER_BRAND = 1) 버려진 별칭은 warnings로 알린다. 검색어 트렌드는 그룹당 키워드 20개까지 별칭 묶음이 가능하다.
